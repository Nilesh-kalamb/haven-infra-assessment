# B1 — The Glacier Cost Gotcha

## 1. Problem

Haven stores photos of sold property listings in Amazon S3. The current lifecycle configuration transitions these photos to S3 Glacier Flexible Retrieval 30 days after upload.

A seller requests deletion on day 40, and the application immediately deletes the photo.

Although the object is deleted, Amazon S3 can still charge for the remaining minimum storage duration.

## 2. Actual Cost Impact

The configured storage class is `GLACIER`, which represents S3 Glacier Flexible Retrieval.

S3 Glacier Flexible Retrieval has a minimum storage duration of 90 days.

If an object is deleted before completing this minimum period, AWS applies a prorated early-deletion charge for the remaining storage duration.

### Example

| Event | Day | Details |
|---|---:|---|
| Photo uploaded | 0 | Stored in S3 Standard |
| Lifecycle transition | 30 | Photo moves to Glacier Flexible Retrieval |
| Seller requests deletion | 40 | Photo is deleted immediately |
| Actual Glacier storage duration | 10 days | Only 10 of 90 days completed |
| Remaining minimum duration | 80 days | Early-deletion charge applies |

The seller's deletion request does not eliminate the minimum storage-duration charge.

For this example, Haven can incur an additional charge equivalent to 80 days of Glacier storage for the deleted object's billable size.

The charge is prorated based on the remaining minimum storage duration and the applicable regional storage rate.

The actual dollar amount depends on the AWS region, object size, storage pricing and billing period.

AWS also charges additional metadata storage for Glacier Flexible Retrieval objects:
- 8 KB per object at S3 Standard rates.
- 32 KB per object at Glacier Flexible Retrieval rates.

These additional costs can become significant when Haven archives a large number of small property photos.

## 3. Why the Existing Lifecycle Design Is Dangerous

The current lifecycle policy archives objects after only 30 days.

However, the application allows sellers to request deletion after archival.

This creates a mismatch between the application's deletion behavior and Glacier's minimum storage-duration requirement.

The main problems are:

1. Early-deletion charges are generated when objects are deleted before 90 days.
2. Large numbers of deleted photos can create unexpected storage costs.
3. Small objects can incur additional metadata and transition request costs.
4. Lifecycle transitions and expiration are asynchronous, so billing behavior must not be assumed to match the physical deletion or transition time.
5. Without billing monitoring, these charges can remain unnoticed until the monthly AWS bill arrives.

## 4. Proposed Lifecycle Redesign

I would redesign the lifecycle policy around the business retention and deletion requirements instead of archiving every sold listing photo automatically after 30 days.

### A. Keep deletion-eligible photos in S3 Standard

Keep photos in S3 Standard while sellers are allowed to request deletion.

S3 Standard does not have the 90-day minimum storage-duration requirement associated with Glacier Flexible Retrieval.

If a seller requests deletion during this period, the application can delete the photo without incurring a Glacier early-deletion charge.

### B. Introduce an archive eligibility period

Define a clear retention and deletion-request window with the business team.

For example:

- Day 0: Photo uploaded.
- Day 0–90: Photo remains in S3 Standard and can be deleted immediately when requested.
- After day 90: Photos that remain eligible for long-term retention can be marked for archival.
- Eligible photos can transition to Glacier Flexible Retrieval.

The 90-day period is an example policy and should be confirmed against business and legal retention requirements.

### C. Use tags or prefixes to control archival

Use object tags or dedicated prefixes to distinguish photos eligible for archival.

For example:

`archive_eligible = true`

The lifecycle configuration should filter eligible objects rather than indiscriminately transitioning every photo.

The application should only mark an object as archive-eligible after its deletion-request window has closed.

### D. Handle deletion requests explicitly

Implement an application-level deletion workflow:

1. Receive the seller's deletion request.
2. Identify the corresponding S3 object.
3. Check its current storage class and retention requirements.
4. Delete it immediately when deletion is permitted.
5. Record the deletion result for auditing.
6. Track any unavoidable early-deletion charges for objects already archived.

**Important:** If sellers can request immediate deletion at any time, even after archival, no lifecycle configuration can eliminate Glacier's early-deletion charge while also guaranteeing immediate deletion. In that case, keep those objects in a storage class without a minimum-duration commitment, or explicitly budget for the early-deletion cost. Legal deletion requirements must not be delayed merely to avoid storage charges.

## 5. Cost Monitoring and Prevention

I would introduce the following cost-control measures:

- Enable AWS Cost and Usage Reports (CUR) to track detailed S3 storage charges.
- Monitor the `EarlyDelete-ByteHrs` usage type for Glacier Flexible Retrieval early-deletion charges.
- Configure AWS Budgets with alerts for unexpected S3 storage expenditure.
- Use AWS Cost Anomaly Detection to identify unusual increases in storage costs.
- Use S3 Storage Lens and S3 Inventory to understand object counts, sizes and storage-class distribution.
- Apply the `landlord_account_id` cost-allocation tag consistently to support landlord-level billing.
- Review lifecycle transition request costs and additional per-object metadata overhead, particularly for small photos.

## 6. Conclusion

The main issue is that Haven transitions photos to Glacier after 30 days without considering the possibility of seller deletion requests during Glacier's 90-day minimum storage period.

My recommendation is to keep deletion-eligible photos in S3 Standard, introduce a clearly defined retention and archive-eligibility period, and transition only objects that are expected to remain archived for at least 90 days.

For objects that must remain immediately deletable after archival, Haven should avoid storage classes with minimum-duration commitments or explicitly account for early-deletion charges.

This approach aligns the storage lifecycle with application behavior, prevents avoidable early-deletion costs and improves AWS cost visibility.
